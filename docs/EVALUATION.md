# EVALUATION — VIMLORE 코드 심층 평가와 완성 전략

> 이 문서는 **완성을 가로막는 진짜 리스크**를 파악하고, 그에 맞는 설계 태도·단계를
> 제시한다. 새 AI는 [`HANDOFF.md`](HANDOFF.md)와 이 문서를 함께 읽어야 한다.
> 측정 시점: 2026-11-10 (엔진 med/low 수정 진행 중, oracle 142/142).

---

## 1. 규모 (정량)

| 지표 | 값 |
|---|---|
| 총 라인 (src+tools+tests) | **~10,000줄**, 45개 파일 |
| 핵심 엔진 `engine.ts` | **2,423줄** — 전체의 ~24% |
| 게임 로직 (core/game) | ~1,300줄 |
| 컨텐츠 (content/chapters) | ~2,600줄 (10챕터 + 그리모어 83개 명령) |
| UI (ui/) | ~1,950줄 |
| 도구/테스트 (tools+tests) | ~1,700줄 |

**구조는 건강하다.** `core/vim`(엔진) / `core/game`(규칙) / `content`(데이터) / `ui`(셸)로
계층이 분리되어 있고, 의존성은 아래쪽(`ui → game → vim`)으로만 흐른다. 컨텐츠는 순수
데이터라 **챕터/스테이지 추가는 코드 수정 없이 가능**하다(AGENTS.md "one-line change").

---

## 2. 복잡성 — 진짜 리스크는 여기다

`src/core/vim/engine.ts`는:
- **~100개 메서드, 149개 `switch`/`case`, 285개 `if`/`else`** 를 가진 단일 클래스.
- 사실상 "Vim의 축소판" 상태머신(모드·오퍼레이터·텍스트 객체·ex·레지스터·매크로·jumplist를
  한 클래스에서 처리)이라 **본질적으로 복잡**하다.

**이 복잡성이 곧 버그의 온상이다.** 이번 세션에서 142/142 oracle이 통과하는데도
실제 vim과 다른 엣지케이스 버그가 **23건** 숨어 있던 것이 증거다. 결론:

> engine.ts의 복잡성은 줄일 수 없다(Vim을 흉내내는 일이 본질적으로 복잡). 따라서
> **"복잡성을 없애는 것"이 아니라 "복잡성을 기계적으로 검증하는 것"**이 완성 전략의 핵심이다.

---

## 3. 확장·버그 수정 가망성 (영역별)

| 영역 | 확장 난이도 | 버그 리스크 | 안전망 |
|---|---|---|---|
| 컨텐츠(챕터/스테이지) | **쉬움** | 낮음 | `lint:levels`가 par·gating·win 재현 검증 |
| UI | 쉬움~보통 | 낮음 | Playwright 수동 검증 |
| 게임 규칙(session/goals/trials) | 보통 | 중간 | `npm test` |
| **엔진(vim/)** | **어려움** | **높음** | **oracle-diff가 유일하고 확실한 안전망** |

**가망성 판단**: 이 프로젝트는 완성 가능하다. 단, 엔진 수정은 반드시 oracle-driven이어야
하고, 그렇지 않으면 142/142이 통과하는데도 버그가 누적되는 실패 모드로 빠진다.

## 4. 구조적 개선점 (우선순위 순)

### 4-1. [높음] oracle 커버리지가 얕음 → **fuzz/property 테스트 도입**
현재 126→133개 케이스는 "손으로 고른" 정상 경로 위주라 엣지케이스(빈 태그, 중첩 괄호,
count+operator 교차 등)가 빠졌고, 그게 버그 23건으로 드러났다.
**권장**: `tools/oracle-fuzz.ts`를 만들어 (1) 시드 기반으로 무작위 버퍼×무작위 키스트로크를
생성하고 (2) 같은 입력을 실제 vim과 engine에 넣어 buffer+cursor를 비교. 몇천 건만 돌려도
숨은 엣지케이스를 대거 발굴한다. jumplist는 1케이스=1프로세스로(아래 함정 참고).

### 4-2. [높음] CI에 vim이 없음 → 검증 갭 인지
`.github/workflows/ci.yml`은 `npm test`(vim-expected.json 스냅샷)로 엔진을 검증하지만,
실제 vim과의 diff는 **로컬에서만** 가능하다. 이 갭을 메우려면 (a) oracle을 GitHub Actions에
`vim` 설치하고 돌리는 job 추가, 또는 (b) fuzz 결과 스냅샷을 커밋해 CI가 회귀를 잡게 하는 것.

### 4-3. [중간] `engine.ts` 2,423줄 단일 클래스 → **완성 후 리팩터링**
모드별(insert/normal/ex/visual)·기능별로 파일을 나누면 유지보수가 쉬워진다. **단, 지금 하지
마라.** 버그 수정 중 대규모 이동은 회귀를 양산한다. "먼저 oracle green + 완성, 그다음 구조 개선".

### 4-4. [중간] 커리큘럼 정합성 자동 검증 부재
`lint:levels`는 gating을 보지만, **"stage.teaches에 적힌 스킬이 solution에 실제로 쓰이는지"**,
**"unlocks에 있지만 어느 스테이지에서도 연습 안 하는 스킬"**은 검사하지 않는다. `tools/level-lint.ts`에
이 두 검사를 추가하면 "특정 스킬만 반복 숙달" 설계 원칙이 자동으로 지켜진다.

### 4-5. [낮음] jumplist oracle 오염
oracle-diff가 모든 케이스를 한 vim 프로세스에서 순차 실행해 jump list가 누수된다.
fuzz/추가 검증 시 `<C-o>`/`<C-i>`는 반드시 별도 프로세스로.

## 5. 설계 태도 (본질 — 이걸 지켜라)

1. **"실제 Vim과의 diff가 유일한 진실"이다.** 어떤 직관·추측·깔끔함도 oracle 통과보다 우선하지
   않는다. 의심되면 vim을 실행해 확인하라.
2. **"재현 케이스가 곧 명세"다.** 모든 버그는 `tools/cases.ts`의 케이스로 먼저 번역되어야
   수정을 시작한다. 케이스 없는 수정은 하지 않는다.
3. **"작은 증분 + 항상 green"이다.** 한 번에 버그 하나. 각 단계에서 oracle·lint·test·tsc가
   전부 green인 상태를 유지해야 어디서 깨졌는지 알 수 있다.
4. **"컨텐츠는 데이터, 엔진은 정밀기계"다.** 스테이지를 고치려고 엔진의 Vim 의미론을 바꾸면
   절대 안 된다(AGENTS.md 불변식). 레벨이 안 풀리면 레벨을 고쳐라.
5. **"완성은 검증 게이트의 합"이다.** 코드가 아니라 다음 4개가 전부 통과해야 완료다:
   `oracle-diff` · `lint:levels` · `npm test`+`tsc` · `doc-check`.

---

## 6. 단계 로드맵 (완성을 위한 순서)

1. **엔진 버그 전량 수정** (진행 중인 med/low 포함) — oracle-driven, 케이스 먼저.
2. **fuzz 테스트 도입** — 숨은 엣지케이스 발굴 + 발견된 버그 수정.
3. **커리큘럼 정합성 자동화** — level-lint에 teaches/unlocks 검증 추가.
4. **성능 재측정·최적화** — desktop 60fps 목표.
5. **실제 플레이 전수 회귀** — Playwright로 게이팅·UI·에러·vim 동작 일치 확인.
6. **(선택) engine.ts 분할 리팩터링** — 완성·배포 후, 회귀 테스트 보호 아래.

각 단계의 "완료"는 §5-5의 4개 게이트 전부 통과로 정의한다.

---

## 7. 한 문장 요약

> VIMLORE는 구조적으로 건강하고 완성 가능한 프로젝트이며, 유일한 실질 리스크는
> **`engine.ts`의 본질적 복잡성**이다. 이를 "기계적 oracle 검증 + 재현 케이스 우선 +
> 작은 증분"으로 통제하는 것, 그리고 커버리지의 얇음을 fuzz 테스트로 메우는 것이
> 완성의 핵심이다.
